# システム要件を定義する

業務要件の原本と抽出物を照合し、実装可能で追跡可能なシステム要件の下書きを作る。

## 入力

- 原本: `docs/requirements/business/<案件名>/source/`。内容を変更しない。
- 読み取り用の抽出物: 同案件の `extracted/`
- 関係するコード、設計書、既存のシステム要件、`docs/requirements/glossary.md`

原本がWordまたはExcelだけで抽出物がなければ、利用可能な文書・表計算ツールで内容と表を保持してMarkdownへ抽出する。変換結果は `extracted/` に保存し、原本との差異や読み取れなかった箇所を明示する。

## 進め方

1. 原本の版、対象範囲、出典位置を確認する。原本と抽出物が食い違う場合は原本を優先する。
2. 既存の実装と設計を調べ、既存機能、制約、用語との関係を整理する。
3. 機能要件と非機能要件を分け、安定した要件IDを付ける。既存IDは再採番しない。
4. 各要件に、観測可能な受け入れ条件、対象アプリ、業務要件の出典を記載する。
5. 対象外、仮定、矛盾、不明点、実現上の懸念を分けて列挙する。解釈や水準を推測で確定しない。
6. 新しい業務用語を用語集へ反映する。確定済みのシステム要件を変える必要があれば、直接確定せず変更案と影響を提示する。
7. 新規または変更中の文書は`draft`として保存する。確認者が内容を合意した後にだけ`approved`へ変更し、確認日と変更履歴を記録する。

新規文書には [assets/system-requirements-template.md](assets/system-requirements-template.md) を使う。

## 完了条件

- `docs/requirements/system/<案件名>.md` に要件、受け入れ条件、対応表、確認事項がある。
- すべての要件が原本の出典または明示した追加制約に追跡できる。
- 原本の変更、未確認事項の断定、実装詳細への過度な固定がない。

出力時は、作成・更新したファイル、主要な確認事項、抽出品質の懸念を報告する。
