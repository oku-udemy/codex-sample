# 計画に沿って実装する

変更の目的、範囲、検証条件を計画に残し、テストと文書を含めて完了させる。

## 計画

1. 要件、受け入れ条件、関連設計、変更箇所に適用される `AGENTS.md` を読む。
2. コードを調査し、変更範囲、変えない範囲、設計判断、テスト、文書更新、リスクを整理する。
3. 新規計画には [assets/plan-template.md](assets/plan-template.md) を使い、`docs/plans/<作業ID>.md` に保存する。外部チケットIDがなければ、目的を表すkebab-caseの識別子を使う。
4. 不可逆な変更、高リスクな設計変更、要件の曖昧さがある場合は実装前に利用者へ確認する。それ以外は計画を提示したうえで作業を続ける。

## 実装と検証

- 既存のパターンに合わせ、小さく役割の明確な変更を行う。
- 新しい振る舞いには先にテストを用意し、失敗理由が意図した未実装部分であることを確かめる。詳細が必要な場合は `test-first` を使う。
- 進捗、計画からの変更、判断理由を計画ファイルへ反映する。
- 変更に応じて `npm test`、`npm run lint`、`npm run build`、必要なら `npm run test:e2e` を実行する。対象workspaceだけで十分な途中検証では `--workspace` を使ってよい。
- 実装と契約・設計が変わった場合は、同じ変更で関係文書も更新する。

## 完了条件

- 対応する受け入れ条件を満たし、対象テスト、lint、buildが成功している。
- 計画ファイルが実際の変更、設計判断、検証結果を反映している。
- 未実施の検証や残課題が明記されている。

レビュー依頼文が必要なら [assets/pr-description-template.md](assets/pr-description-template.md) を使う。外部サービスへの投稿は、利用者が明示的に依頼した場合だけ行う。
