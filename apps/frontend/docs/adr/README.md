# Architecture Decision Record運用

## 目的

Frontendへ長期的な影響を与える設計判断について、背景、選択肢、決定理由、影響を記録します。実装から理由を推測して過去の判断を作るのではなく、今後行う判断を記録します。

## 対象範囲

次のような、複数の選択肢があり後から理由を参照する価値がある判断を対象とします。

- 状態管理やデータ取得ライブラリの導入
- ルーティング方式の採用
- FrontendとBackend間のAPI型共有またはコード生成
- コンポーネント構成やデザインシステムの大幅な変更
- テスト基盤、ビルド方式、配信方式の変更

小さなリファクタリング、容易に取り消せる局所的変更、単なる作業記録は対象外です。

## 現行仕様

- ADRファイルはこのディレクトリへ配置します。
- ファイル名は`NNNN-kebab-case-title.md`とし、`0001`から連番にします。
- ADRは1つの判断だけを扱います。
- 一度承認したADRの判断内容は書き換えず、変更時は新しいADRから置き換え元を参照します。
- ReactやViteなど既に採用済みの技術は、当時の背景と選択肢を確認できないため、遡ってADRを作成しません。

### ステータス

| ステータス | 意味                                           |
| ---------- | ---------------------------------------------- |
| `提案`     | レビュー中で、まだ実装判断として確定していない |
| `承認`     | 採用が決まり、実装の根拠として有効             |
| `却下`     | 検討したが採用しなかった                       |
| `置換`     | 後続ADRによって判断が置き換えられた            |
| `廃止`     | 判断が不要になり、代替ADRも存在しない          |

## ADRテンプレート

新規ADRは次の形式で作成します。

```md
# NNNN: 判断を表す短いタイトル

- ステータス: 提案
- 日付: YYYY-MM-DD
- 決定者: 名前またはチーム

## 背景

判断が必要になった状況、制約、解決する問題を記載する。

## 判断基準

選択肢を評価するうえで重要な条件を記載する。

## 検討した選択肢

- 選択肢A
- 選択肢B

## 決定

採用する選択肢と、その理由を記載する。

## 影響

好影響、トレードオフ、移行や運用上の注意を記載する。

## 関連情報

関連するIssue、設計書、実装へのリンクを記載する。
```

## 改善候補

- ADRが増えた時点で、このREADMEへ番号、タイトル、ステータスの索引を追加する。
- レビューフローが定まった場合は、決定者と承認条件を具体化する。
