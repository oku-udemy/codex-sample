# Frontendテスト戦略

## 目的

Frontendの公開動作を効率よく検証するため、テストレベルごとの責務、追加基準、実行方法、現行の検証範囲を定義します。

## 対象範囲

- Vitest、Testing Library、jsdomによるFrontendコンポーネントテスト
- PlaywrightによるFrontendとBackendを接続したE2Eテスト
- Frontendに対するビルド、lint、フォーマット確認

Backend単体のテスト方針は対象外です。

## 現行仕様

### テストレベルの責務

| レベル         | 実行環境                       | 主な責務                                                 | 外部依存                              |
| -------------- | ------------------------------ | -------------------------------------------------------- | ------------------------------------- |
| コンポーネント | Vitest + jsdom                 | 表示状態、利用者操作、API呼び出し、state反映、エラー表示 | `fetch`をモックする                   |
| E2E            | Playwright + 実ブラウザー      | FrontendとBackendを通した主要導線とブラウザー上の表示    | ローカルのFrontend・Backendを起動する |
| 静的検証       | TypeScript + ESLint + Prettier | 型、規約、フォーマット                                   | なし                                  |

実装詳細ではなく、利用者が認識できる文言、ロール、ラベル、状態変化を優先して検証します。

### 現在のコンポーネントテスト

`apps/frontend/tests/App.test.tsx`は次を検証します。

- 読み込み中表示からTodo一覧へ遷移する。
- Todoを入力・追加し、POST要求と追加後の表示を確認する。
- チェックボックスで完了状態を更新し、完了件数へ反映する。
- Todoを削除し、最後の1件なら空状態へ遷移する。
- APIのエラーメッセージを`alert`として表示する。

テストごとに`fetch`を置き換え、実際の外部サービスへ接続しません。共通のDOMマッチャーは`apps/frontend/tests/setup.ts`で設定します。

### 現在のE2Eテスト

`e2e/todo.spec.ts`は次を検証します。

- Todoを追加し、完了にして、削除する一連の主要導線。
- 初期取得が500エラーになった場合のエラー表示。

Playwrightは`playwright.config.ts`の`webServer`設定によりFrontendとBackendを起動します。通常は1ワーカー相当の直列実行とし、CIでは失敗時に最大2回再試行します。最初の再試行時にトレースを記録します。

### 実行コマンド

リポジトリルートから実行します。

| コマンド                                  | 内容                                 |
| ----------------------------------------- | ------------------------------------ |
| `npm test`                                | 各workspaceのテストを実行            |
| `npm run test --workspace @todo/frontend` | Frontendのコンポーネントテストを実行 |
| `npm run test:e2e`                        | Playwright E2Eテストを実行           |
| `npm run lint`                            | 全workspaceを静的解析                |
| `npm run build`                           | FrontendとBackendを型検査・ビルド    |
| `npm run format:check`                    | Prettierによる形式確認               |

### テスト追加基準

- 画面の分岐や状態遷移を追加・変更した場合は、コンポーネントテストを追加または更新します。
- API要求のパス、メソッド、body、応答反映を変更した場合は、コンポーネントテストで契約を確認します。
- 利用者の主要導線、FrontendとBackendの接続、ブラウザー固有動作を変更した場合は、E2Eテストを追加または更新します。
- 不具合を修正する場合は、可能な限り修正前に失敗し修正後に成功する回帰テストを追加します。
- CSSだけの変更でも操作可能性や表示状態が変わる場合は、適切なレベルのテストを更新します。

## 必須シナリオ

| 分類             | シナリオ                          | 現在の自動テスト       |
| ---------------- | --------------------------------- | ---------------------- |
| 初期表示         | 読み込み中から一覧へ遷移          | コンポーネント         |
| 初期表示         | 0件で空状態を表示                 | 追加テスト内で間接確認 |
| 初期表示         | 一覧取得失敗を表示                | コンポーネント、E2E    |
| 追加             | 有効なTodoを追加                  | コンポーネント、E2E    |
| 追加             | 空白だけの入力を送信しない        | 未追加                 |
| 追加             | 追加失敗時に入力と一覧を維持      | 未追加                 |
| 更新             | 未完了から完了へ変更              | コンポーネント、E2E    |
| 更新             | 更新失敗時に一覧を維持            | 未追加                 |
| 削除             | Todoを削除                        | コンポーネント、E2E    |
| 削除             | 削除失敗時に一覧を維持            | 未追加                 |
| アクセシビリティ | ラベルとalertを利用して操作・確認 | テスト内で部分的に確認 |
| レスポンシブ     | 520px以下で操作可能               | 未追加                 |

「未追加」は現行仕様の欠落ではなく、自動テスト上の改善余地を示します。

## 改善候補

- 空白入力、追加失敗、更新失敗、削除失敗のコンポーネントテストを追加する。
- 更新・削除要求のメソッド、パス、bodyを明示的に検証する。
- キーボード操作とフォーカス表示のアクセシビリティテストを追加する。
- モバイル相当のviewportで主要導線を確認するE2Eテストを追加する。
- API契約の不一致を検出するテストを導入する。

改善候補は現行のテスト合格条件には含めません。
